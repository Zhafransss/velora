## 2. Rincian pekerjaan

### 2.1 Auth WhatsApp terenkripsi di MySQL (DEC-17)
- Kredensial perangkat dan kunci Signal tiap kanal disimpan di tabel `wa_auth_creds` / `wa_auth_keys`, dienkripsi **di konektor** sebelum ditulis
  (AES-256-GCM, IV acak per record, AAD mengikat channel+jenis+id sehingga baris yang disalin ke kanal lain tidak terbaca). Laravel tidak pernah membaca isinya.
- Kunci dari `AUTH_ENCRYPTION_KEYS` (mendukung rotasi). Kunci salah → konektor **menolak start dan tidak menimpa data**.
- Pool MySQL memakai mode strict (ditemukan: MySQL lokal memotong data panjang secara diam-diam, yang akan merusak sesi).
- Kredensial ikut terhapus saat kanal dihapus; `whatsapp:prune-auth` (mingguan) membersihkan sisa kanal yatim.
- Mode `AUTH_STORE=file` (tanpa enkripsi) tetap ada untuk PoC dan memberi peringatan keras.
- **Belum diuji dengan ponsel:** pairing ulang dan restart tanpa scan. Sesi lama di `connector/auth/` tidak dimigrasi; setiap nomor perlu scan QR ulang saat beralih.

### 2.2 Penyapu pesan menggantung (`messages:sweep-stuck`, tiap 5 menit)

| Keadaan macet | Tindakan | Alasan |
|---|---|---|
| Masuk `received` / balasan `pending` > 5 menit | Diantre ulang | Klaim job atomik, aman diulang |
| Sama, tetapi > 60 menit | Gagal (`stale_expired`) | Membalas berjam-jam kemudian merugikan |
| `processing` > 10 menit | Gagal + kuota dikembalikan | AI mungkin sudah dipanggil; tidak diulang |
| `sending` > 10 menit | Gagal "tidak terkonfirmasi" | Mungkin sudah sampai; tidak dikirim ulang (cegah kirim ganda) |

Pemilik workspace mendapat notifikasi dashboard. Ambang bisa diubah lewat env `SWEEP_*`.

### 2.3 Halaman Pesan Gagal (`/app/failed-messages`)
- Menampilkan pesan gagal 24 jam terakhir dengan penyebab berbahasa awam. Owner/admin workspace dapat **kirim ulang**; viewer hanya melihat.
- **Keputusan Anda: admin platform tidak berhak mengirim WhatsApp**, jadi tidak ada versi admin (ada tes yang menjaga ini).
- Pengaman: peralihan status atomik (anti klik ganda), butuh WhatsApp terhubung, pengiriman "tidak terkonfirmasi" wajib konfirmasi (risiko ganda),
  pesan masuk yang sudah punya balasan tidak diproses ulang, isolasi tenant (id tenant lain = 404).
- **Temuan:** kunci kuota per pesan bersifat idempoten, sehingga memproses ulang pesan yang kuotanya sudah dikembalikan akan memanggil AI gratis.
  Ditambah kolom `messages.process_attempts` agar tiap proses ulang memakai kunci baru (terbukti oleh tes ujung ke ujung).

### 2.4 reCAPTCHA (FR-001)
- `RecaptchaVerifier` bersama untuk form daftar dan form kontak. **Gagal-tertutup:** Google tidak terjangkau atau secret kosong → ditolak.
- Form kontak dulu error 500 saat Google down; kini menampilkan pesan yang rapi.
- Diverifikasi ke Google sungguhan dengan key uji publik Google. `RECAPTCHA_ENABLED=false` hanya untuk lokal/tes.

### 2.5 Backup terenkripsi + uji restore (NFR-005)
- `backup:run` (harian 01:30): mysqldump → gzip → AES-256-GCM berpotongan → unggah ke disk `backup` (S3-kompatibel) → hapus yang melewati masa simpan.
- `backup:verify` (mingguan): restore ke database sementara, bandingkan jumlah baris per tabel dengan manifest, hapus database sementara.
- `backup:status`: exit code ≠ 0 bila backup terakhir > 26 jam atau restore belum teruji > 8 hari (untuk pemantau eksternal).
- `backup:decrypt`: membuka backup menjadi SQL untuk pemulihan bencana. `backup:key`: membuat kunci.
- Terbukti di MySQL lokal: restore 39 tabel cocok; berkas dirusak satu byte / terpotong ditolak; jalur bencana (decrypt + impor) 8 pengguna cocok.
- Retensi bawaan 14 hari, dibatasi maksimal 30 (DEC-15). Runbook: `docs/BACKUP-RESTORE.md`.

## 3. Temuan dan pelajaran penting

| Temuan | Dampak | Tindakan |
|---|---|---|
| `connector/.gitignore` (`auth/`) menelan `connector/src/auth/` | Konektor di `development` tidak bisa start dari clone baru; CI gagal | Diperbaiki menjadi `/auth/`; diverifikasi dengan clone bersih. **Kebiasaan baru:** cek clone bersih bila menambah file baru |
| Kunci kuota idempoten vs proses ulang | AI gratis + hitungan kuota meleset | Kolom `process_attempts` + kunci per percobaan |
| MySQL lokal non-strict | Data terenkripsi bisa terpotong diam-diam | Sesi konektor memakai `STRICT_ALL_TABLES` |
| `Schema::getTableListing()` memuat tabel skema lain di MySQL | Backup gagal | Diganti query `information_schema` terbatas ke database aktif |
| Ekstensi `sodium` tidak aktif di PHP CLI lokal | Enkripsi backup tidak bisa memakainya | Memakai `openssl` AES-GCM |
| `composer audit`: 61 advisory di 19 paket (guzzle, psr7, beberapa paket Filament; sebagian tingkat high) | Risiko keamanan dependensi | **Belum ditangani** — dijadwalkan besok |

## 4. Tindakan yang menunggu Anda

1. **Push `feature/recaptcha-backup` → PR ke `development` → merge**, lalu di mesin Anda: `composer install` dan `php artisan migrate`
   (tabel `backup_runs`; `process_attempts` dan `wa_auth_*` jika belum).
2. Pastikan job CI **`connector`** dan **`pest`** hijau pada `development`; aktifkan *required status checks* di GitHub bila belum.
3. **Cadangkan kunci di password manager:** `AUTH_ENCRYPTION_KEYS` (di `connector/.env`) dan `BACKUP_ENCRYPTION_KEY` (di `.env`). Jangan simpan di server/database/git.
4. Uji dengan ponsel (belum ada bukti): isi `AUTH_STORE=mysql` + `DB_*` di `connector/.env`, scan QR ulang, restart konektor → harus pulih tanpa scan.
   Konfirmasi juga apakah indikator "mengetik" terlihat di ponsel.
5. Pilih penyedia bucket backup (saran: Cloudflare R2) dan buat token khusus bucket.
6. Lokal: bila widget reCAPTCHA error di `127.0.0.1`, set `RECAPTCHA_ENABLED=false` (key produksi terdaftar untuk domain asli).
7. Proses lokal (konektor, `queue:work`) yang saya jalankan dari sesi ini akan mati bila sesi berakhir; jalankan sendiri bila perlu. Penjadwal juga harus jalan (`php artisan schedule:work`) agar penyapu, retensi, dan backup berjalan.

|---|---|
